# PaneCommander 統合レビュー反映・改修指示

## 1. 目的

これまでのユーザーレビュー結果をPaneCommanderへ反映する。

PaneCommanderは、Midnight Commander型の2ペイン操作を基本とし、Windows上で日常的に利用する軽量ファイルマネージャーである。

今回の目的は、既存デザインを大幅に変更することではなく、次の品質を向上させること。

- ファイルマネージャーとしての操作性
- 画面の視認性と一貫性
- 設定の体系化とカスタマイズ性
- Windows標準操作との整合性
- 低CPU・低メモリ消費

既存の実装、仕様、テスト、性能測定資料を確認したうえで、以下のレビュー要求を反映すること。

**重要原則**

1. 既に了承された2ペイン画面の基本構成は維持する。
2. 要求されていない大規模なUI刷新は行わない。
3. WPF/.NET 10の既存構成を基本とする。
4. 新機能の追加によって、アイドルCPUやメモリ消費を不必要に増やさない。
5. 既存機能を破壊しない。特に左右ペイン独立性、タブ状態、キーボード操作、ファイル一覧の仮想化を維持する。
6. 未実装機能は実装済みと報告しない。未達項目は未達のまま記録する。

---

## 2. メイン画面の上部構成

### 2.1 メニュー領域

現在、画面上部左側に表示されている「PaneCommander」という固定文字列を撤去し、その場所をメニュー領域にする。

この領域に以下を左から配置する。

- お気に入り
- 更新
- 設定

現在右上にある同名ボタンは撤去する。

既存ボタンの機能は維持し、単なる位置変更によって動作を変えないこと。

新たな行を追加せず、ファイル一覧に使用できる縦方向の表示領域を維持する。

### 2.2 タイトルバー

Windowsのタイトルバーに固定のアプリ名を表示する代わりに、アクティブペインの選択中タブが示すディレクトリを表示する。

設定によって、表示方法を切り替えられるようにする。

- ディレクトリ名のみ（既定）
- フルパス

例：

- ディレクトリ名のみ：`Documents`
- フルパス：`C:\Users\Example\Documents`

ドライブ直下は `C:\` のように表示する。

以下の操作に追従してタイトルを更新すること。

- 左右ペイン切り替え
- タブ切り替え
- ディレクトリ移動
- パス指定による移動

設定は永続化する。

タイトルバーの背景色・文字色はカラースキーマに連動させる。メイン画面だけでなく、設定ダイアログなども対象とする。

原則としてWindows標準のウィンドウ機能を維持し、DWMなど利用可能な仕組みで対応する。タイトルバーの色変更だけを目的とした全面的な独自タイトルバーの実装は避ける。

## 3. ペインとタブの視認性

### 3.1 選択タブの表示

左右のペインについて、次の3状態を明確に区別する。

**A. アクティブペインの選択タブ**

- アクセントカラーで明確に強調する。
- 背景色と境界線で識別する。
- 文字のコントラストを十分に確保する。

**B. 非アクティブペインの選択タブ**

- 非選択タブと明確に異なる背景色にする。
- アクティブ側よりは控えめだが、現在選択されているタブであることを一目で分かるようにする。
- 落ち着いた青灰色などを基本とし、明確な境界線を付ける。

**C. 非選択タブ**

- 通常背景色を使用する。
- 選択タブと混同しない視認性にする。

色は固定値を各画面へ直接埋め込まず、カラースキーマから取得すること。

ペイン切り替えでタブの選択状態そのものは変更せず、アクティブ／非アクティブの強調表示を更新する。

### 3.2 ペインの状態

現在のアクティブペインの枠線・ヘッダー強調は維持する。

タブの強調とペインの強調が矛盾しないこと。

## 4. 表示カラムの設定

現在の「カラム」ボタンから表示項目を設定できるようにする。

最低限、以下を対象とする。

- 名前
- 種類
- サイズ
- File Age
- 更新日時

要求仕様：

1. カラムの表示／非表示を切り替えられる。
2. カラムの表示順序を変更できる。
3. 列幅を変更できる。
4. 設定した状態を保存し、再起動時に復元する。
5. 左右のペインで独立した設定を持てる。
6. ウィンドウサイズ変更時に不自然な表示崩れを起こさない。
7. 名前列は残り幅を有効活用できるようにする。
8. 列見出しやサイズ値が不用意に途中で切れないようにする。

現在の画面では「サイズ」「File Age」の見出しやファイルサイズが途中で切れている。この問題を改善する。

表示設定とデータのソート条件は区別すること。

## 5. ファイルサイズの表示改善

ファイルサイズをバイト数だけで表示せず、補助単位を使用して読みやすくする。

1024単位で自動変換する。

例：

| バイト数 | 表示 |
|---:|---:|
| 560 | 560 B |
| 65,536 | 64 KB |
| 1,048,576 | 1 MB |
| 4,456,448 | 4.25 MB |
| 1,073,741,824 | 1 GB |

要求仕様：

- B / KB / MB / GB / TBなどへ自動変換する。
- 小数は最大2桁とし、不要な末尾ゼロを表示しない。
- 数値を右揃えにする。
- ディレクトリのサイズは従来どおり `—` とする。
- サイズによるソートは元のバイト数で行う。
- ツールチップなどで正確なバイト数を確認できるようにする。
- 単位を含めて読みやすい列幅にする。

内部のファイルサイズ情報は整数のバイト数で保持し、表示形式によって計算や比較の正確性を失わないこと。

## 6. File Ageの配色改善

現在のFile Age背景色は蛍光色に近く、画面全体の雰囲気から浮いている。

新しいファイルから古いファイルまで色が変化する機能自体は維持し、彩度・明度を調整して落ち着いた配色へ変更する。

要求仕様：

- 新しいファイルと古いファイルの色の違いが分かる。
- 蛍光色や過度に鮮やかな色を避ける。
- ダーク／ライト双方で文字が読める。
- File Ageの背景色をカラースキーマで管理する。
- 個別の色はカラーピッカーで編集できる。
- 既存の経過時間計算および `m / h / d / M / y` の表示仕様は維持する。

File Ageの更新のために高頻度タイマーや不要な全件再描画を導入しないこと。

## 7. 設定画面の再構成

現在の設定画面は多数の項目が縦方向に連続している。

これを設定分類ごとに整理する。

設定全体を一つのテーマで管理するのではなく、**設定分類の一つとして「カラー」を設け、その中にカラースキーマを配置する。**

推奨する分類は以下とする。

### 一般

- 起動時の状態復元
- タイトルバーの表示形式
- その他の一般動作設定

### 表示・レイアウト

- お気に入りサイドバーの表示／非表示
- カラムの表示設定
- 行の高さ
- 行の間隔
- その他の画面配置設定

### カラー

- カラースキーマ選択
- 配色の個別編集
- File Age配色
- タブ・ペイン・スクロールバー等の配色

### フォント

- フォント種類
- 文字サイズ

### ファイル操作

- コピー・移動・削除などの動作設定

### キーボード

- ショートカット関連設定

既存の設定項目は適切な分類へ移し、設定値や保存機能を失わないこと。

未実装項目のために実装済みを装う設定画面を作らないこと。

## 8. カラースキーマ

### 8.1 基本構造

「カラー」分類の中にカラースキーマ選択機能を設ける。

初期プリセット候補：

- Ocean Dark：現在の青緑系ダークテーマを基礎として、彩度を調整
- Graphite：落ち着いたグレー系
- Light：明るい配色

カラースキーマを選ぶと、アプリケーションの配色が統一される。

### 8.2 カラースキーマの対象

- タイトルバー
- メニュー領域
- 設定画面
- ボタン
- お気に入りサイドバー
- ペイン背景
- ペインヘッダー
- アクティブペイン枠線
- アクティブペインの選択タブ
- 非アクティブペインの選択タブ
- 非選択タブ
- ファイル一覧背景
- ファイル一覧文字色
- 選択行
- 列ヘッダー
- File Ageの各時間帯
- スクロールバー
- Fキー操作領域

### 8.3 編集と保存

- プリセットは読み取り専用とする。
- 配色を編集した場合はカスタムスキーマとして保存できる。
- カスタムスキーマには名前を付けられる。
- カスタムスキーマを再選択できる。
- 選択したスキーマを永続化する。
- プリセットの初期配色へ戻す手段を提供する。
- プレビューで適用前に確認できる。

WPFではテーマ色を共通のリソースとして管理し、色の定義が各Viewへ分散しないようにする。

カラースキーマは配色のみを変更し、フォント・列幅・行の高さなどの設定を変更しない。

## 9. カラーピッカー

現在の `#RRGGBB` の直接入力は維持したうえで、カラーピッカーを追加する。

要求仕様：

1. 各色設定欄に現在の色を表示する色見本を設置する。
2. 色見本をクリックするとカラーピッカーを開く。
3. ピッカーで選択した色を `#RRGGBB` へ反映する。
4. コードを直接入力した場合も色見本を更新する。
5. 不正なカラーコードは検証し、保存できないようにする。
6. 色変更はプレビューへ即時反映する。
7. キャンセルでは未保存変更を破棄する。
8. 保存・適用で確定し、次回起動時も復元する。

同じ色選択部品を各項目で再利用する。

---

## 10. フォント選択

現在のフォント名を直接入力するUIを改善し、Windowsにインストールされているフォントから選択できるようにする。

要求仕様：

- 利用可能なフォントをドロップダウンリストに表示する。
- フォント名による検索・絞り込みを可能にする。
- 日本語フォント名に対応する。
- 選択したフォントをプレビューに反映する。
- フォントサイズ設定と連動する。
- 設定を保存・復元する。
- 設定済みフォントが利用できない場合は安全な既定フォントへフォールバックする。

WPFの `Fonts.SystemFontFamilies` などを利用できる。

フォント変更後もカラム見出しや一覧表示が崩れないこと。

## 11. スクロールバーのデザイン

現在のスクロールバーは白色のWindows標準スタイルが目立ち、ダークテーマと統一されていない。

カラースキーマに連動したスクロールバースタイルを作成する。

要求仕様：

- トラックを画面背景に馴染む色にする。
- つまみは通常時に落ち着いた色を使用する。
- ホバー・ドラッグ時は操作可能であることが分かる色にする。
- 幅は12px程度を基本として操作性を確保する。
- 上下ボタンを残す場合も同じ配色にする。
- ライトスキーマにも対応する。
- ファイル一覧だけでなく設定画面などにも適用する。

WPF標準のスクロール機能・仮想化を維持すること。

装飾のための常時アニメーションやタイマーを導入しない。

## 12. お気に入り登録

現在開いているタブのディレクトリを、お気に入りへ登録できるようにする。

要求仕様：

- 選択中タブをお気に入りに追加できる。
- お気に入り領域の `＋` ボタンから登録できる。
- タブをお気に入り領域へドラッグ＆ドロップして登録できる。
- 同一パスの重複登録を防止する。
- 登録したお気に入りは永続化する。
- お気に入りを選択すると対象ディレクトリへ移動できる。
- 登録済みのお気に入りを解除できる。

タブのドラッグによるお気に入り登録と、ファイル・フォルダーのドラッグによる移動・コピーは区別すること。

## 13. リンク・再解析ポイントの操作

現在、一覧に表示されたリンクを選択してEnterを押すと「再解析ポイントは非対応です」と表示される。

ファイルマネージャーとして、この一律拒否を解消すること。

対象：

- ディレクトリのシンボリックリンク
- ファイルのシンボリックリンク
- ジャンクション
- Windowsショートカット（.lnk）は別形式として扱い、対応方針を明確にする

要求仕様：

1. ディレクトリを指すリンクは、Enterで対象ディレクトリを開く。
2. ファイルを指すリンクは、Enterで対象ファイルを開く。
3. リンク切れの場合は適切なエラーを表示する。
4. アクセス拒否の場合はアクセス拒否として表示する。
5. リンクをたどった後も戻る・進む・上位への移動が正しく動く。
6. 循環リンクを無限にたどらない。
7. リンクの種類によって動作が違う場合は、その違いを明確にする。

`Cookies` や `Application Data` などWindowsの互換ジャンクションは、アクセス自体が拒否される場合がある。

その際に「機能非対応」と誤表示しないこと。

また、コピー・移動・削除時には、**リンクそのものを扱う操作とリンク先の実体を扱う操作を明確に区別**すること。

特に削除時に、意図せずリンク先のディレクトリ配下を削除しないこと。

## 14. Tabキーによるペイン切り替え

現在、Tabキーで左右ペインを切り替えた際に、キーボードフォーカスがスクロールバーへ移動する問題がある。

この不具合を修正する。

期待動作：

- Tabでアクティブペインが左右交互に切り替わる。
- 切り替え先のファイル一覧へキーボードフォーカスを移す。
- 選択中の項目があれば、その選択位置を維持する。
- 切り替え後の上下キーは対象ペインの一覧を操作する。
- Enterは切り替え先の選択項目に作用する。
- Tabを連続して押しても正しく左右交互に切り替わる。
- スクロール位置を不必要に変更しない。
- スクロールバーや列ヘッダーに意図せずフォーカスを移さない。

メインのファイル一覧操作中に限ってTabキーをペイン切り替えとして処理し、入力ダイアログや設定画面では通常のTabフォーカス移動を維持する。

WPFの標準Tab移動と競合しないよう、キーイベントの処理順序とフォーカス制御を確認すること。

アクティブペインを示す表示と、実際のキーボードフォーカスを一致させる。

## 15. ドラッグ＆ドロップによるファイル操作

ドラッグ＆ドロップはPaneCommanderに必要な機能とする。

対象：

- 左右ペイン間
- 同一ペイン内のフォルダー
- 異なるフォルダー
- WindowsエクスプローラーからPaneCommander
- PaneCommanderからWindowsエクスプローラー

要求仕様：

1. ファイルとフォルダーに対応する。
2. 複数選択した項目をまとめて扱える。
3. コピーと移動を区別できる。
4. Ctrl / Shiftなどの標準的な修飾キー操作に対応する。
5. 実行される操作をドラッグ中に視覚的に示す。
6. フォルダー上へドロップできる。
7. 同一フォルダーへの移動など、成立しない操作を適切に扱う。
8. ファイル名の競合や上書き確認に対応する。
9. アクセス拒否やI/Oエラーを適切に通知する。
10. 操作失敗時にデータを失わない。
11. 実際に成立した操作とUIの表示状態を一致させる。

Windowsの標準的なファイル操作の意味に合わせる。

独自のドラッグ＆ドロップ処理によって、ファイル一覧の仮想化や既存のキーボード操作を破壊しないこと。

ファイル操作基盤がM4に属する場合は、その基盤と統合して実装すること。

## 16. 描画方式と性能

### 16.1 既存調査結果

これまでの比較測定で、次の結果を確認している。

| 条件 | Private Bytes |
|---|---:|
| 空のWPF画面 | 約140MB |
| 実画面・2タブ | 約198MB |
| 実画面・6タブ | 約272MB |

追加4タブの保持データは、GC後の管理メモリで約0.38MB。

一方、2タブから6タブで増加したPrivate Bytes約75MBは、診断限定のソフトウェア描画では約9MBまで縮小した。

この結果は、タブ数に伴う描画経路のリソース増加を強く示唆する。

ただし、WPF／Direct3D／GPUドライバー等の具体的な割り当て元は未特定である。

したがって、増加を単純にWPFの固定費として扱わないこと。

### 16.2 今回の実装に対する制約

- 非表示タブの描画要素を不必要に保持しない。
- カラースキーマ切り替えによるリソース増加を確認する。
- スクロールバースタイル変更によるリソース増加を確認する。
- フォント変更によるリソース増加を確認する。
- 描画のための常時更新処理を追加しない。
- ファイル一覧の仮想化を維持する。
- 診断結果を製品コードの改善効果と混同しない。

GPU描画の有効／無効をユーザー設定として提供する案については、既存の描画方式設定と調査結果を確認して評価すること。

ソフトウェア描画はメモリ削減に効果がある可能性があるが、描画速度・スクロール操作・CPU負荷との比較が必要である。

**描画方式を強制的に切り替えたり、ソフトウェア描画を唯一の正解として固定したりしない。**

既存設定に再起動が必要な場合は、その仕様を正確に表示する。

### 16.3 性能目標

これまでの暫定目標を継続して使用する。

- 起動時Private Bytes：150MB以下
- 通常使用・6タブ：200MB以下
- 大量ファイル表示：300MB以下
- アイドルCPU：0%近傍
- アイドル時の不要なファイルI/Oなし
- 長時間利用でリソースが増加し続けないこと

目標未達の場合、その結果を正確に記録すること。

単にGCを強制して一時的な数値を下げることで合格としない。

WPF基礎コストが大きいことは確認されているが、目標の緩和は自動的に行わない。必要な場合は実測に基づく別途判断事項として報告する。

## 17. 実装順序

既存実装を調査して完了済み項目を特定し、未対応部分だけを実装する。

推奨順序は次のとおり。

### 第1段階：既存操作の不具合修正

- Tabキーによるフォーカス移動
- リンク／ジャンクションのEnter操作
- サイズ列の表示改善
- 列幅の切れ方の改善

### 第2段階：画面・設定構造の改修

- 上部メニューの再配置
- タイトルバーの表示形式とテーマ連動
- タブ選択色
- 設定画面の分類
- カラム設定
- フォント選択
